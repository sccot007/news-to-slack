쿠버네티스 헬스 체크가 실수로 서비스를 깨우고 있습니다. 해결 방법은 다음과 같습니다.

CNCF Blog · 2026-07-29
이 페이지는 Gemini/Anthropic으로 자동 번역되었습니다.

스케일-투-제로(Scale-to-zero)는 헬스 체크가 다시 스케일업할 때 문제가 생깁니다. KubeElasti의 ProbeResponse가 쿠버네티스 서비스를 진정으로 유휴 상태로 유지하면서 로드 밸런서와 업타임 모니터를 만족시키는 방법을 알아보세요. 스케일-투-제로는 이론상 완벽해 보입니다.

유휴 서비스. 파드 없음. 청구 없음.

그런데 프로덕션에 배포하면 아무도 경고하지 않은 문제를 발견하게 됩니다. 로드 밸런서가 파드가 의도적으로 사라졌다는 것을 알지 못합니다. 계속 헬스 체크를 보냅니다. 모든 헬스 체크가 리졸버(resolver)를 타격합니다. 리졸버는 직무를 다하며 트래픽을 스케일업 신호로 해석합니다. 파드가 깨어납니다.

유휴 파드에 대한 비용을 다시 지불하게 됩니다.

이것은 KubeElasti의 버그가 아닙니다. 현대 인프라가 어떻게 연결되는지에 대한 근본적인 긴장 관계입니다. 로드 밸런서는 서비스가 살아있다는 것을 알아야 합니다. 쿠버네티스 오토스케일러는 서비스가 죽었다는 것을 알아야 합니다. 이 두 가지는 첫 번째 팀이 클라우드 로드 밸런서 뒤에서 제로 레플리카 배포를 실행하려고 시도한 이후로 계속 충돌했습니다.

KubeElasti의 새로운 ProbeResponse 기능이 이러한 긴장을 직접 해결합니다.

아무도 말하지 않는 문제

대부분의 프로덕션 환경에서 스케일-투-제로가 어떻게 무너지는지 보여드리겠습니다:

서비스를 10분의 비활성 후에 스케일다운하도록 구성합니다.

로드 밸런서는 30초마다 헬스 체크를 수행하도록 설정되어 있습니다.

마지막 파드가 종료되는 순간, 두 가지 일이 동시에 발생합니다:

쿠버네티스 서비스는 이제 KubeElasti의 리졸버를 가리키고 있습니다.

로드 밸런서가 GET /healthz를 보냅니다.

리졸버가 요청을 받습니다. KubeElasti에게 들어오는 모든 요청은 신호입니다: "누군가 이 서비스가 필요합니다." 리졸버가 운영자에게 알립니다. 운영자가 스케일업을 시작합니다.

유휴 상태에 도달하지 않았습니다. 작업 부하를 계속 깨우는 30초 루프를 추가했을 뿐입니다.

이 문제는 세 가지 뚜렷한 형태로 나타납니다:

클라우드 로드 밸런서 AWS ALB, GCP Load Balancer, Azure Application Gateway — 모두 트래픽을 안전하게 라우팅하기 위해 정기적인 헬스 체크가 필요합니다. 이러한 체크는 빈번하고 무자비하며 "의도적으로 유휴" 개념을 이해하지 못합니다.

쿠버네티스 Liveness 및 Readiness 프로브(Probes) 파드에 구성된 내부 프로브도 수신 계층에서 복제되는 경우가 많습니다. 제로로 스케일된 서비스이지만 업타임 모니터에 등록된 서비스는 요청을 트리거합니다.

플랫폼 모니터링 내부 개발자 플랫폼, Istio 같은 서비스 메시 그리고 Prometheus Blackbox Exporter 같은 관찰성 스택은 엔드포인트를 지속적으로 프로브하여 가용성을 주장합니다. 이들 중 어느 것도 저하된 서비스와 의도적으로 유휴 상태인 서비스를 구별하지 않습니다.

결과: 스케일-투-제로를 구성한 팀들은 모니터링 스택이 제로 상태를 유지하도록 절대 허용하지 않기 때문에 잠재적 절감액의 정확히 0%를 달성합니다.

왜 기존의 관례가 작동하지 않는가

일반적인 조언은 헬스 체크 엔드포인트 라우팅을 애플리케이션 라우팅과 분리하는 것입니다. "헬스 체크를 다른 서비스에 배치하세요"라고 사람들은 제안합니다.

이것은 세 가지 이유로 작동하지 않습니다:

첫째, 헬스 체크 구성을 항상 제어할 수 없습니다. 클라우드 로드 밸런서는 서비스가 등록된 IP와 포트를 확인합니다. AWS ALB에 /healthz에 다른 백엔드를 사용하도록 지시할 수 없습니다.

둘째, 라우팅을 분리하면 팀이 절대 유지하지 않는 운영 복잡성을 만듭니다. 시간이 지나면서 표류가 발생합니다. 헬스 체크가 어쨌든 애플리케이션 엔드포인트를 타격하기 시작합니다.

셋째, 가장 중요하게는: 헬스 체크 엔드포인트는 애플리케이션 엔드포인트입니다. /healthz 경로가 경로입니다. 재라우팅은 목적을 무효화합니다.

다른 도구들은 서비스가 실행 중일 때도 프록시를 요청 경로에 영구적으로 유지하여 이를 해결합니다. 항상 헬스 체크를 가로챌 수 있는 능력을 위해 지연성을 교환합니다. 작동하지만, 시간이 지남에 따라 악화되는 아키텍처 트레이드오프입니다.

ProbeResponse는 어떻게 작동하는가

KubeElasti의 ProbeResponse 기능은 리졸버에 직접 매칭 레이어를 추가합니다.

서비스가 제로로 스케일될 때, 리졸버는 이미 들어오는 모든 트래픽을 가로채고 있습니다. ProbeResponse를 사용하면 리졸버가 스케일업 알림을 결정하기 전에 평가하는 규칙을 정의할 수 있습니다.

요청이 프로브 규칙과 일치하면, 리졸버는 정의한 상태 코드와 본문으로 직접 응답하며 운영자에게 알리지 않습니다. 작업 부하는 제로를 유지합니다. 헬스 체크는 200 OK를 받습니다. 모두가 행복합니다.

구성이 어떻게 보이는지는 다음과 같습니다:

probeResponse: - method: GET path: type: PathPrefix value: /healthz response: status: 200 body: '{"ok":true}' - method: HEAD path: type: Exact value: /ready response: status: 204 body: '{}'

매칭 규칙은 다음을 지원합니다:

HTTP 메서드 (GET, HEAD, POST 등)

경로 매칭: Exact, PathPrefix 또는 RegularExpression

헤더 매처 (모두 AND)

쿼리 매개변수 매처 (모두 AND)

규칙은 위에서 아래로 평가됩니다. 첫 번째 일치가 승리합니다. 규칙이 일치하지 않으면 정상 동작이 적용됩니다 — 요청이 큐에 대기하고 스케일업을 트리거합니다.

이 디자인은 의도적입니다. ProbeResponse는 스케일링 교체가 아닌 게이트입니다. 실제 트래픽은 여전히 서비스를 깨웁니다. 합성 헬스 트래픽은 합성 상태로 남습니다.

아키텍처 인사이트

ProbeResponse가 "/healthz를 항상 켜져 있는 별도의 파드로 라우팅"과 같은 핵(hack)과 다른 점은 지능이 어디에 있는지입니다.

KubeElasti의 아키텍처에서, 리졸버는 이미 프록시 모드 중 가로채기 레이어입니다. 프로브 매칭을 여기에 추가하는 것은 아키텍처상 비용이 없습니다 — 추가 홉 없음, 추가 구성요소 없음, 항상 켜져 있는 프록시 오버헤드 없음.

서비스가 활성 파드를 가질 때, 리졸버는 완전히 요청 경로 밖에 있습니다. KubeElasti는 제공 모드(serve mode)로 전환하고 트래픽을 파드로 직접 라우팅합니다. ProbeResponse 규칙은 리졸버가 활성일 때만 적용되며, 이는 서비스가 제로 레플리카일 때만입니다.

이는 다음을 의미합니다:

서비스가 실행 중일 때 지연성 페널티 없음

프로브 처리를 유지할 인프라 오버헤드 없음

헬스 체크 라우팅을 위한 별도의 배포나 서비스 없음

실제 요청을 큐에 대기하고 스케일업을 트리거하는 동일한 리졸버는 단순히 결정을 내리기 전에 메모리 내 규칙 세트를 확인합니다. 서비스가 활성일 때는 진정한 의미에서 비용이 없습니다.

실제 영향

이것이 경제학을 바꾸는 몇 가지 시나리오를 생각해보세요:

내부 개발 서비스

팀은 종종 내부 도구 — CI 미리보기 환경, 내부 대시보드, 테스트 서비스 — 를 실행하는데, 이들은 존재해야 하지만 실제 트래픽을 거의 받지 않습니다. ProbeResponse를 사용하면, 플랫폼 모니터링이 30초마다 확인하더라도 이러한 서비스는 실제 사용 세션 사이에 제로 상태를 유지합니다.

GPU 작업 부하

GPU 파드는 비싸습니다. 팀이 GPU 서비스를 제로로 스케일하지 않는 주요 이유는 헬스 체크로 인한 콜드 스타트를 용인할 수 없기 때문입니다. ProbeResponse는 진정한 GPU 유휴 시간을 가능하게 합니다 — 리졸버에서 헬스 체크에 응답하고, 실제 추론 트래픽이 도착할 때까지 GPU 파드를 종료된 상태로 유지합니다.

라이선스 소프트웨어

실행 중인 인스턴스별로 요금을 청구하는 엔터프라이즈 소프트웨어는 진정으로 필요할 때까지 꺼져 있어야 합니다. 헬스 체크 트래픽은 "필요"하지 않습니다. ProbeResponse가 그 구별을 강제합니다.

East-West 트래픽

내부 마이크로서비스는 종종 실제 트래픽을 보내기 전에 헬스 체크 경로에서 서로 호출합니다. Istio 같은 서비스 메시는 정기적인 연결성 확인을 실행할 수 있습니다. ProbeResponse는 조기 스케일업을 트리거하지 않고 이를 처리할 수 있습니다.

실제 권장사항

ProbeResponse를 구성하기 전에 헬스 체크 소스를 감사하세요:

클라우드 로드 밸런서 헬스 체크 구성을 확인하세요 — 경로, 메서드 및 빈도를 식별합니다.

쿠버네티스 수신 주석을 검토하세요 — NGINX, Traefik 및 Istio 모두 구성 가능한 헬스 체크 동작이 있습니다.

업타임 모니터링을 확인하세요 — Prometheus Blackbox Exporter, Datadog 합성 모니터 또는 다른 외부 업타임 도구를 사용 중이면 프로브하는 엔드포인트를 기록하세요.

서비스 메시 구성을 검토하세요 — Istio, Linkerd 및 유사한 도구는 종종 사이드카 동작의 일부로 헬스 체크를 실행합니다.

각 헬스 체크 소스에 대해 해당 ProbeResponse 규칙을 만드세요. 광범위한 커버리지를 위해 PathPrefix를 사용하고 (예: /health/ 아래의 모든 경로) 특정 엔드포인트의 경우 Exact를 사용하세요.

보수적인 응답 본문을 설정하세요. 실제 서비스가 건강한 상태에서 반환하는 것을 반환하세요. 모니터링 스택이 응답 본문을 검증하면, ProbeResponse가 정확히 일치해야 합니다.

헤더와 쿼리 매개변수 매처를 사용하여 동일한 경로를 공유할 때 헬스 체크와 실제 트래픽을 구별하세요. 일부 모니터링 도구는 이를 구별하는 데 사용할 수 있는 식별 헤더를 설정합니다.

KubeElasti의 관점

스케일-투-제로는 항상 두 부분 문제였습니다.

첫 번째 부분 — 제로로 스케일다운, 요청 큐 대기, 스케일업 — 은 눈에 띄는 문제입니다. 강연, 블로그 게시물 및 기능 비교에 나타나는 문제입니다.

두 번째 부분 — 주변 인프라 노이즈에도 불구하고 제로를 유지 — 은 스케일-투-제로가 이론적 값을 전달하는지 결정하는 실제 문제입니다.

ProbeResponse는 두 번째 부분에 대한 KubeElasti의 답입니다.

ProbeResponse 없이 KubeElasti를 배포하는 팀은 종종 부분적 절감을 봅니다. 서비스가 제로로 스케일되고 헬스 체크로 인해 즉시 스케일업되며, 쿨다운 기간 동안 활성 상태를 유지하고 사이클이 반복됩니다. 로그는 스케일업 이벤트를 표시하지만 해당하는 사용자 트래픽은 없습니다.

ProbeResponse가 그 루프를 닫습니다.

적절하게 구성된 cooldownPeriod과 결합할 때, ProbeResponse는 진정한 유휴 시간 — 서비스가 정말로 꺼져 있는 구간을 가능하게 합니다. 단순히 헬스 체크 주기 사이의 시간이 아닙니다.

GPU 작업 부하, 라이선스 소프트웨어 또는 고주파 내부 서비스가 있는 팀의 경우, 이것이 개념 증명과 프로덕션 등급 비용 절감 사이의 차이입니다.

결론

헬스 체크는 선택 사항이 아닙니다. 클라우드 로드 밸런서가 이를 요구합니다. 서비스 메시가 이에 의존합니다. 플랫폼 모니터링이 이를 필요로 합니다.

스케일-투-제로도 선택 사항이 아닙니다 — 인프라 효율성에 진지하다면 말입니다.

수년간, 이 두 요구 사항 사이의 긴장은 팀들을 타협으로 강요했습니다: 항상 켜져 있는 프록시, 별도의 헬스 체크 서비스, 또는 가장 중요한 서비스에서 스케일-투-제로를 포기합니다.

ProbeResponse가 그 타협을 제거합니다.

헬스 체크는 200 OK를 받습니다. 작업 부하는 제로를 유지합니다. 인프라 비용은 모니터링 오버헤드가 아닌 실제 사용을 반영합니다.

그것이 진정한 스케일-투-제로의 모습입니다.

핵심 요점

헬스 체크는 스케일-투-제로가 프로덕션에서 절감을 전달하지 못하는 가장 일반적인 이유입니다.

ProbeResponse를 사용하면 KubeElasti 리졸버가 구성된 프로브 요청에 직접 응답하여 스케일업을 트리거하지 않습니다.

규칙은 메서드, 경로 (Exact/PathPrefix/Regex), 헤더 및 쿼리 매개변수에서 일치합니다.

ProbeResponse는 프록시 모드에서만 적용됩니다 — 서비스가 실행 중일 때 오버헤드 없음

GPU 작업 부하, 라이선스 소프트웨어 및 내부 서비스가 이 기능으로부터 가장 많은 이점을 얻습니다.

ProbeResponse를 구성하기 전에 헬스 체크 소스를 감사하세요 — 클라우드 LB, 서비스 메시, 업타임 모니터 및 수신 컨트롤러가 모두 독립적으로 프로브합니다.
